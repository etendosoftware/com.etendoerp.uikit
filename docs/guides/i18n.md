# Labels and formatting

> **STATUS: shipped.** `OB.UIKit.labels`, `OB.UIKit.t` and `OB.UIKit.fmt` are in the runtime.
> Read §4 before you assume a deployed window is translated: it is not, and that is a known
> limitation rather than a bug you can fix in JavaScript.

## 1. No string in a uikit window is written in source

Every piece of visible text comes from `AD_MESSAGE`, reached by key. The runtime holds one flat
map, filled by the bundle before the app runs:

```js
OB.UIKit.labels({
  ETDEMO_Title: 'Order cockpit',
  ETDEMO_Overdue: 'Overdue'
});
```

and read back one key at a time:

```js
var heading = OB.UIKit.t('ETDEMO_Title');
```

`OB.UIKit.t` returns **the key itself** when there is no label for it. That is deliberate: a
missing `AD_MESSAGE` row shows up on the screen as `ETDEMO_Overdue` — ugly, obvious, and
searchable — instead of rendering as an empty box that nobody notices until a customer does.

Keys are prefixed by module (`ETUIK_` for the runtime, `ETOKRS_` for the OKR sample), and the
manifest's `labels` entry lists the prefixes a window needs. A key that no prefix covers is simply
absent at runtime.

## 2. The rows the runtime itself needs

The runtime ships two label keys of its own and uses two more for accessibility. All four degrade
to a hardcoded English fallback when the row is missing, so a window still works without them —
but a screen reader then announces English inside a Spanish instance, which is why they should be
inserted.

| key | used by | placeholders |
| --- | --- | --- |
| `ETUIK_Loading` | the first-load block | — |
| `ETUIK_LoadFailed` | the first-load error block | — |
| `ETUIK_RailAria` | `OB.UIKit.rail`, as its `aria-label` | `%{progress}`, `%{expected}` |
| `ETUIK_MeterAria` | `OB.UIKit.meter`, as its `aria-label` | `%{score}`, `%{target}` |

Placeholders are `%{name}`, substituted by a private helper inside the runtime. An unknown name is
left in place rather than replaced with `undefined`, so a bad row is visible instead of silent.
There is no public interpolation function: app text that needs a variable should compose it with
`OB.UIKit.html`, where the escaping is handled.

Both instruments render without their label. `OB.UIKit.rail` falls back to `"62% / 71%"` and
`OB.UIKit.meter` to `"0.68 / 0.80"`, which is worse prose and correct information.

## 3. Numbers, money and dates

`OB.UIKit.fmt(value, kind, opts)` formats one value and **never throws**. Eight kinds:

| kind | mask | notes |
| --- | --- | --- |
| `number` | `#,##0.00` | the general case |
| `int` | `#,##0` | counts |
| `qty` | `#,##0.###` | quantities keep three decimals |
| `price` | `#,##0.00` | pass `opts.currency` |
| `amount` | `#,##0.00` | pass `opts.currency` |
| `pct` | `#,##0.0` | appends `%` |
| `date` | `OB.Format.date` | from the session |
| `dateTime` | `OB.Format.dateTime` | from the session |

```js
var cells = [
  OB.UIKit.fmt(1234.5, 'amount', { currency: 'EUR' }),
  OB.UIKit.fmt(62.5, 'pct'),
  OB.UIKit.fmt('2026-09-30', 'date')
];
```

Three things about this function are worth knowing before you use it.

**`pct` takes percentage points, not a fraction.** `62.5` renders as `62.5%`. That is what every
pace calculation in the kit produces and what `OB.UIKit.rail` consumes, so the two agree.

**It never invents a currency.** There is no session currency in the client, so `price` and
`amount` print a bare number unless you pass `opts.currency` with the symbol or the ISO code *the
datasource returned next to the amount*. An amount whose currency was guessed is not money, it is
a number with a decoration on it. Two amounts in different currencies in one column is a reporting
bug, and it is the datasource's job to resolve, not this function's.

**It degrades instead of failing.** `OB.Format` is not in the source tree — it is generated per
request by core's `application-js.ftl`, which publishes `defaultDecimalSymbol`,
`defaultGroupingSymbol`, `defaultGroupingSize`, `date` and `dateTime` — so a test harness, an
early script or a stripped instance may not have it at all. Without it `OB.UIKit.fmt` returns
`String(value)`. A screen showing `1234.5` is still a working screen; a screen showing an
exception is not.

Dates are parsed from the `yyyy-MM-dd` that `UikQuery.date` emits, through the local-time `Date`
constructor rather than `Date.parse`. `Date.parse` reads a bare `yyyy-MM-dd` as UTC, which moves a
business date back by one day for every user west of Greenwich — a reliably reported, reliably
misdiagnosed bug.

Formatting happens at **render** time, never in state. State must be JSON-serializable (see
`docs/guides/actions-and-permissions.md`), so keep the number and the ISO string and format on the
way to the screen.

## 4. Labels are baked in at deploy time

`verify/deploy-view.mjs` reads the `AD_MESSAGE` rows and writes them into the bundle as an
`OB.UIKit.labels` call. That keeps the runtime free of a per-request lookup — and it freezes the
window in one language:

Every user gets the labels as they read at deploy time, whatever their own language is. Two
consequences for anyone working on a window:

1. **Editing an `AD_MESSAGE` row does not change a deployed window.** Re-run `deploy-view.mjs`.
   A label that "did not update" is almost always this.
2. **A multi-language instance is not supported yet.** Fixing it means the template reads labels
   per request, at which point the bundle stops being a static file. That is a deliberate later
   decision, recorded here so nobody re-discovers it as a defect.

Until then: write the keys, insert the rows, and do not build anything that depends on a per-user
language at runtime.
